## §2 我的实错（逐条认，含补测）

### E1｜§5.1 的数字跨场景搬用（红队 + 工程席各点一次，成立）
- **932 MB 是 concat 的；187.5 MB 是"逐帧即弃**＋直写磁盘**"的**——我把它并排引用，等于拿两个不同程序的数比较。
- **补测（同一 27.27 MB / 85922 帧日志，`process.resourceUsage().maxRSS` 内核高水位）**：

| 模式 | maxRSS | external 峰值 | 耗时 |
|---|---|---|---|
| concat（**插件现用**） | **922.9 MB** | 1536.9 MB | 10.3 s |
| stream（逐帧即弃，不返回全文） | **211.5 MB** | 61.4 MB | 4.1 s |
| dump（逐帧即弃 + 直写磁盘） | **191.0 MB** | 56.5 MB | 5.8 s |

- **插件的 `decodeSessionLog` 必须返回全文** ⇒ 改逐帧即弃后的真实峰值 ≈ **200–300 MB**（红队推断值；`{text}` 返回时最终 UTF-16 串 ≈ 105 MB 省不掉）。**"932→187" 这句话作废。**
- 另有**语义风险**（工程席实测）：`L3537` 的正则 `[\s\S]{0,400}` **可跨帧**（`"type":"user/message"` 与 `"source":{"kind":"user"` 分落相邻两帧时逐帧扫会漏匹配）⇒ **逐帧化不是零风险改动**，须选：(a) 只去掉整份 `Buffer.concat` 拷贝（语义零风险、收益有限）；(b) 改 API 为逐帧迭代器 + 重写两个调用方 + 同步 `_test-raw-decode.mjs`。

### E2｜§2.4 的 rg 性能：口径错配 **且原测无效**（红队点出，成立且比我以为的更糟）
- **红队的口径质疑成立**：我测的是 70 文件/318 MB（**均值 4.54 MB/文件**），而真实缓存是 1066 文件/166 MB（**均值 0.156 MB/文件**）——**差 29 倍**。
- **更糟**：我重测时发现**原数字根本是无效测量**——`Start-Process -ArgumentList <数组>` 传中文 pattern 时**参数被吞**，rg 把**路径当成了正则**（stderr: `regex parse error: (?:C:\...\corpus)`），**它一次都没扫语料**，那 0.08–0.17 s 是启动失败的时间。
- **重测（真实形态 1066 文件 / 169.4 MB，带自证：命中场景真有输出、exit code 正确）**：

| 场景 | 峰值 | 耗时 | 输出行 |
|---|---|---|---|
| 无命中（全扫） | 8.4 MB | **0.393 s** | 0 |
| 罕见命中 | 8.3 MB | 0.251 s | 0（该字面量确不在过滤后正文里） |
| 海量命中（`-c`） | 8.8 MB | 0.484 s | 1066 |
| 全量输出 `-n -m5` | 9.3 MB | **0.623 s** | 4684 |

- **结论"不上索引"仍成立**（0.25–0.62 s、8–9 MB），但**方案里的 0.08–0.17 s / 8–15 MB 必须替换成这组数**。
- **教训（已犯第二次同类）**：Windows 上 `Start-Process -ArgumentList` 传数组 + 非 ASCII 参数不可靠；**测量必须带自证断言**（输出非空 / exit code 正确），否则"跑通了"是假象。

### E3｜§5.2 是 5 处不是 6 处，真雷在水位量纲（工程席）
`L3077`（`max(mtime)` + `sum(size)`）/ `L3439`（sum 后**历史 `wm.frames` 量纲失配 ⇒ 必须迁移**）/ `L3530` / `L5773→L5793/L5808`（`extractMessageFlowAsync` 只吃单文件+帧水位 ⇒ 须升 `(file, frame)` 二元）/ `L8370`。
**最锋利且原稿完全没提**：`readUnitCache(sid, curFrames)`（`L3331`）的陈旧判据是 `L3342 d.frames > curFrames ⇒ 陈旧`，写入端在 `L5985`。**存 sum 而读单文件 ⇒ 恒判陈旧 ⇒ 每轮全量重提取；存单文件而读 sum ⇒ 早半段永不进单元。**（我文档里还把签名写成 `readUnitCache(curFrames)`——**错**。）

### E4｜§3.4 的 `time` 归并键（工程席实测反例）
`reasoning-chunks` / `tool-call-chunks` / `text-chunks` **100% 只有 `time0`/`seq0`、无 `time`**；`session` 头用 `createdAt`。当前 KEEP 的 5 类今天确实都有 `time`（成立），**但 §3.2 自己留的 `--with-reasoning` 一开就整批失效**。
→ **改：主排序键 `(文件序, 帧序, 行序)`**（必然存在，且与"行号=事件级定位"同构），`time` **降级为展示 + overlap 校验**。

### E5｜§3.2 的错误判据：我写的是**错的**（实测裁决，两席与我各有说法）
- 我原稿写 `/"error"|"is_error":true/` —— **蛇形 `is_error` 实测命中 0**；子串 `"error"` 会**误命中正文含 error 字样的成功结果**。
- 工程席主张"写死 `data.error`" —— **会漏**。跨 18 个日志实测出 **3 例 `A=false B=true`**：`content[].isError=true` 而 **`data.error = undefined`**，正文均为 `Error: sandbox escalation to …`（内层 `run_code` 调用失败，外层未置 error）。
- **裁决：判据 = `content[].isError === true`（B，实测为 A 的超集）**，可写 `data.error != null || content[].isError === true`。首日志 132 例上 A/B/文本嗅探三者等价（各 15），**但等价只在那个样本成立**。

### E6｜§3.2 的正文抽取：naive 实现会吞进 reasoning（工程席）
`assistant/message` 正文确在 `data.message.content[]`（`data.content` 路径 0 命中 ✓），但 **48 条里 12 条（25%）没有任何 `type:"text"` 块**，且 **`reasoning` 块也带 `text` 字段** ⇒ 若写成 `content.map(b => b.text)` 会把 **reasoning 全文**收进来，与"不含 reasoning"自相矛盾且体积暴涨。
→ **必须 `filter(b.type === "text")`，并单独计数打印"类内空正文"。** 另：`compaction/summary` 两席样本均 0 条 ⇒ **KEEP 里这一类无实测覆盖，门必须专门夹具**。

### E7｜§6/§8 编号不一致（提案人）
§6 是 G1–G11，§8 写"J1~J11" → 统一编号（本文采用 **R1–R18**）。

### E8｜§2.1「等于没有链接」措辞过强（提案人 + 红队各点一次）
日期已把 1066 个 sid 缩到 1/365，且工具输出的 sid 恰好补上锚点。准确表述是「**不够直接**」，不是「零帮助」——过强的措辞会把"用上 616 处日期锚点"这条便宜路径一起否掉。

## §3 我接受的设计变更

### C1｜按天分片（红队）——**接受，但修正分片键**
- 原主张：`session-text/<YYYY-MM-DD>.jsonl`，只对今天增量、历史冻结。**收益**：一刀砍掉跨天 sid 归并 / overlap 检测 / 全库水位 / "size 变小→全量重建"；R2/R9/R11 的爆炸半径从全库缩到一天。
- **反例（我补）**：§2.2 那 7 个劈开会话**本身跨天**（早半段 09-10、晚半段 09-16）⇒ 按事件日期分片会把**同一会话劈到两个分片**，"整会话时间线"不可得。
- **裁决：分片键 = sid 的归属日（其日志最大 mtime 所在日）**，分片内容 = 该 sid **全部文件**。冻结条件 = 该 sid 所有日志 mtime 都早于今天。跨天的 7 例会整体落到 `2026-09-16`，完整性保住。

### C2｜段文件 + manifest（工程席）——**接受**
原 §3.5 的"增量只解新帧、原子 rename 整档重写" = **省 CPU 不省 I/O**（最大 sid 实测 60.1 M 字符 ≈ 80 MB，每次查询前增量 = 一次 80 MB 重写）。改为：

```
~/.dsh/session-text/<归属日>/<sid>/manifest.json     ← 唯一可变点，原子替换
                                  /seg-0001.jsonl    ← 写一次、永不修改
```
增量 = 只写新 `seg` + 原子换 `manifest`；检索 = rg 扫整个目录树；定位从"行号"升级为 **`seg/行`**。

### C3｜身份键 = 目录 + 帧 0 头的 `session.id`（根因席）——**接受**
不用"两个已知文件名"作候选集（防 DSH 再改名成 v4 → **第三个文件静默漏收**）。改为：扫目录取**全部** `.zstd`，逐个验帧 0 头 `session.id` 与目录 sid 相符即并入；`time` 仅作排序/展示。

### C4｜水位 = 源文件 + 已消费字节偏移 + 该处帧内容摘要（根因席）——**接受**
帧计数不是身份（伪 magic / 坏帧 / 扫描器版本变化会让"第 k 帧"错位）。且**"半截帧下次补回来"只在宿主继续写完该帧时成立**——进程被杀留下的是**永久残帧**，必须与"坏帧只丢该帧 + 记账"配套。

### C5｜`limit` 截断 ⇒ 静默假阴性（根因席）——**接受，定 P0**
rg 是遍历序，`--limit N` 只是"遍历到的前 N 行"，最相关的那条可能落在 limit 之外 → 不报错、有结果、结果都是真的 → 用户读成"原文里没这句"。
→ **必做**：先 `rg --count` 拿总数，**永远打印「命中 N 处（其中列出 M 条）」**，**绝不把截断后的条数当命中数**。这一条原稿完全漏了。

### C6｜坐标不变量（根因席）——**接受，定 P0**
§3.7 把**物理文件名**与**行号**并排打成 `session.jsonl.zstd:1204`，而 1204 是**缓存行号**、源文件是 zstd 二进制**无法按行读**；且口径版本一变（全量重建）**所有行号整体漂移**，被写进笔记的引用**静默腐烂**。
→ **缓存行号只许用于同一次调用内的二次访问**；`--show` 接受**源坐标**（sid + 源文件 + 帧号/字节偏移）；每处坐标带坐标系标签（`cache:#1204` / `src:<file>#f12@0x1A3C`）。
配套两条同级前提：**幂等可复算**（两次构建逐字节相同——读时构建没有单一写者，不一致时无法区分 bug 与数据更新）；**无损或有账**（丢弃计数从"打印"升级为**长期指标**）。

### C7｜root 覆盖（回归门席）——**接受，列 P1 前置**
否则 R1–R18 只能污染真库（713 MB / 全量 123 s）。须支持 `--sessions-root` / `--cache-dir` / `DSH_HOME`。

### C8｜取峰值内存用 `process.resourceUsage().maxRSS`（回归门席）——**接受并已交叉验证**
内核维护高水位，**不依赖采样时机**（这正是我 `setInterval` 失效的原因：同步循环饿死事件循环）。实测 stream=**202.7 / 211.5 MB** vs 外部轮询 **198.0 MB**，吻合。
`Start-Process -Wait` 后 `PeakWorkingSet64` 取 0 的原因也确认：`-Wait` 返回的是**创建时快照**，进程已退出、句柄已释放。

### C9｜Variant 仪式替代鉴别仪式（回归门席）——**接受**
本方案是全新工具，**没有"上一版字节"可比**。改：工具内置隐藏开关 `SELFTEST_BUG=<id>`（`concat` / `no-incremental` / `single-file` / `size-watermark` / `inplace-write` / `touch-every-run` / `rg-missing`），门在每种变体下**必须红在指定编号**，门头写死 `id→门` 映射。**没有这个开关，门的 FAIL 形态无法演示，等于门没被证明过。**

### C10｜盖章入 P1（根因席 + 红队**独立同结论**）——**接受，改判**
原稿 §4 把「盖 sid 章」列为"可以永远不做"。两席独立指出：**它正是 166 MB 全库缓存存在的唯一原因**。
- 机制：归档侧 prompt `L5827` **已逐字打印完整 `session.id`**，产物却是"以日期命名的日档"——条目记的是**中间产物的名字**，不是来源身份。且插件**从不解析 `[ses …]`**（无校验/无回填/无检索）⇒ 零选择压力 ⇒ 标签收敛为最省力的日期（实测 **616~619 处、0 处 id 形**）。
- **收益**：盖章后「已知会话」场景**根本不需要缓存**（单 sid 直解：典型 0.66 MB→0.1 s，最大 27.3 MB→4.7 s），缓存只剩"跨会话关键词搜"一个用途——**规模与优先级双双下降**。
- **代价**：需改插件 + 重启（与"零插件改动"的原始卖点冲突）→ **列为本轮最需要用户拍板的一条**。

### C11｜§5.2 移出本期，只加可见性（红队）——**接受**
修它 = **账本迁移**（`archiveWatermarks` 重算 + `archivedSessions` 消号）→ 独立一期。本期只加"目录内两个候选同时存在 → `cwarn`"。

### C12｜其余接受的条目
- 提案人 B1/B2/B7/B8 + J1–J4（行号体系统一为 `cache:#N`；JSONL 换行**交给 `JSON.stringify` 单次编码**、禁手工二次转义；`.meta.json` 同款 tmp+rename；编号统一；**chunk-vs-final 必须计数器化**）
- 回归门席 R12 并发 / R13 rg 缺失（**实测 `rg` 不在 PATH** ✓）/ R14 编码 / R15 路径 / R17 可发现性 / R18 运行账本
- 工程席：`runBackupNow` **不备份** `session-text/` → 写进 §4（否则将来会问"备份里为什么没有它"）
- 回归门席：G5 的"7 个真实案例"**降级为真机观测**（会被轮转/删除，不能当门），门用合成夹具
- 回归门席：G1 是**同义反复**（"size 未变就跳过"必然 0 重写）；G2 只断言逐行相等是**假门**，须加"本次实际解码帧数 < 文件总帧数"；G4 补"缓存行数 === 事件数"；G11 补"rg 占用时 rename"（Windows EPERM/EBUSY）

- **但采集端也必须修**：≥8 MB 的 0.37% 是**缺陷级**（不是压缩取舍），值得单独一期

### 11.5 两个独立的损失机制（不要混为一谈）

| # | 机制 | 量级 | 性质 |
|---|---|---|---|
| **L1** | **普遍采样损失**（per-message 800/1000 字符上限 + 帧采样） | 保留 ~17%、字面量召回 ~15% | **结构性权衡**（归档本就是浓缩），但 15% 偏低，有优化空间 |
| **L2** | **≥8 MB 阈值悬崖** | 保留 **0.37%**、召回 **1.5%** | **缺陷**（30× 落差 + 零告警），应修 |
