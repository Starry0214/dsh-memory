## 新发现的风险/缺陷（按等级，指到文件:行）

### P1 — 重火路径不观察结果 ⇒ pending 清理覆盖不完整（MF1 残余）
`index.js:15120-15124`（maint finally 重火）与 `index.js:15373-15377`（spawn finally 重火）都是
`setTimeout(() => { try { spawnIntentCheckpoint(...) } catch(e){} }, 0)`——**Promise 被丢弃**。
后果：T4 的 queued 项在重火时若以 `retry:false` 终态失败（如 `retry-breaker`、`subagents-unavailable`、`bad-structure`），
`intentRetryFail`（15208）只做记账/入队，**没人调 `p3T4PendingCleanup`** ⇒ `checkpointPendingAt` 残留到 TTL（60min），期间 T5 被 `p3T5PendingActive` 压住（21443）。
审计 MF1 原话要求把清理"挂到**所有** spawn 路径：15320、15066（重火）与 INTENT_PENDING 淘汰"——淘汰那条做了（15248），**重火两条没做**。
（注：自述 §1 MF1 只写"两处 queued 重火**透传**"，未声称挂了清理 ⇒ 自述没撒谎，是**实现未达审计原文**。）

### P2 — T4 记账 S2 改动造成失败重复计数 + queued 误记失败
`index.js:18356-18357`：
```js
p3CostBump("checkpointWrite", { n: _ok?1:0, ..., ok:_ok?1:0, fail:_ok?0:1 }, { trigger:"T4", ... })
```
① **失败重复计**：T4 失败时 `intentRetryFail` 已记 `{fail:1, trigger:"I-fail"}`（15214），T4 又记一条 `fail:1` ⇒ 一次失败在账本里计 **2 次 fail**（S2 想修的"先成功后失败"变成了"失败两次"）。
② **queued 误记失败**：忙入队返回 `{ok:false,queued:true}` ⇒ `_ok=false` ⇒ 记 `fail:1`，可这一轮什么都没失败（后续重火成功还会再记 `I-ok`）。
消费方：`p3-cost.js:272-277`（`failOf`）→ `fails.total/byKind` 直接进面板（`:370,379`）⇒ **用户可见的"检查点失败数"被放大**。
对照：T5 用纯函数 `p3T5OutcomeRecord`（7045-7056）把 `queued` 的 `fail` 记为 0、`dup` 记为 0——T4 这条缺同一口径。
（T1 的同款写法在 21396-21398，属**本批之前**既有，不计入本批回归，但同源建议一并收口。）

### P3 — 淘汰清 pending 无时间戳校验，可能误清"更新的一次 T4"
`index.js:15248` 调 `p3T4PendingCleanup(_evVal.sessionId, null, "queued-evict")`，而 `p3T4PendingCleanup`（7037-7038）**无条件**把该会话 `checkpointPendingAt` 置 0。
路径：会话 S 的 T4#1 忙入队（pending=T1）→ S 发生新压缩 T4#2（pending=T2，覆盖）→ 队列淘汰 T4#1 ⇒ 清掉的是 T2 ⇒ T5 在 T4#2 仍在写时即可触发 ⇒ 双写（两个 writer、新 cid 绕开 dup 幂等）。
概率低（需同会话在队列里堆两条 + 淘汰），但代价是重复子代理/tokens。

### P3 — 自述 §3 声称的 `retry-cwd-missing` 事件**不存在**
自述 §3："`.monitor.json events`：新增 `t4-pending-cleared reason=…`、**`retry-cwd-missing`（旧条目无 cwd 时）**"。
实测 `grep retry-cwd-missing index.js` = **0 处**。`t4-pending-cleared` 确有（7040）、`pending-evict`/`pending-dedupe` 确有（15243/15255）。
影响：`.integrate.json` 里 4.5.11 之前的旧队列条目（无 `cwd` 字段）在目标会话已不 live 时会静默走 `_targetCwd=""` 分支（见下条），**无任何留痕**。
（当前实测队列为空：`intentRetry` = 0 条，所以是潜在风险而非现网问题。）

### P3 — `_targetCwd` 空串时的归属退化（db 写"当日主题"、md 写"通用块"，且无观测）
`index.js:8867-8908`：`if (cwd && sid8)` 才走 P2.5 会话主题；cwd 为空 ⇒ 落到 D8「会话检查点」线的**当日 `YYYY-MM-DD` 主题**（8951 的句头也只有 cid/sid，**没有 cwd**）。
`index.js:15345`：md 路径 `_cw=""` ⇒ `_secKey=""` ⇒ 写通用块。
可达路径：`opts.cwd` 空 + `parentAgent` 无 cwd + 目标会话不 live（`agentsBySession.get(sessionId)` 无值），即 15231 的三级兜底全空。
影响：检查点写进跨项目共享的日线（不丢，但归属丢失）；且该句没有 `· cwd` ⇒ **读侧防御对它天然失效**（不误杀，但不防御）。

### P3 — 读侧防御的正则未锚定句首，且不覆盖 D8 日期主题句
`index.js:9023`：`/·\s*cwd\s+([^\n）)]+)/.exec(text)` 是对**整段**文本的首次匹配（非 `^` 锚定、非首行限定）。
① 正常情况首行就是 `## 检查点（… · cwd <cwd>）`（`p25-topics.js:283-294`）⇒ 命中头 ✓；
② 若某条检查点句是**旧格式**（无 cwd）而正文里恰出现 `· cwd X` 字样 ⇒ 会把正文里的 cwd 当归属比较，可能**误杀正常桥接**（模型正文出现该字样的概率极低，但不是 0）；
③ D8 日期主题句（8951）没有 cwd 字段 ⇒ 这条防御**不覆盖**该路径（对应上一条的退化场景）。
建议：把正则锚到首行/`^## 检查点` 内，或直接解析 `buildCheckpointHeader` 的固定字段。

## 失效路径（≥3 条；实列 7 条）

1. **重火终态失败 ⇒ T5 被压 60min**：T4 忙入队 → 队列项重火 → `subagents-unavailable`/熔断 ⇒ `intentRetryFail` 返回 `retry:false`，重火路径丢弃结果（15123/15376）⇒ `checkpointPendingAt` 不清 ⇒ `p3T5PendingActive` 为真 60min ⇒ 若会话在这 60min 内归档，**永久无检查点**。

3. **cwd 解析全空 ⇒ 归属退化**：`session.header.cwd` 缺失 + `opts.cwd` 空 + 目标会话不 live ⇒ `_targetCwd=""`（15231）⇒ db 写 D8 **当日主题**（8867 跳过 P2.5 分支）、md 写通用块（15345）⇒ 跨项目共享线被写入且**无事件留痕**（`retry-cwd-missing` 不存在）。

6. **T1/T5 cid 变更 + R2 `_cpId` 正则 ⇒ "本次✓"永不出现**：`index.js:18503` `/压缩\s+([0-9a-f]{8})/i` 对 `p3t1-<sid8>-<b36>` / `p3e-<sid8>-<b36>` 的 `cid8`（如 `p3t1-bca`）永不匹配 ⇒ `checkpointIsCurrent` 恒 false（18512/18516）。**修复前同样不匹配**（旧 `p3t1-ses` 亦非 8 位 hex）⇒ 非本批引入（自述 S4 已如实标注为待办），但 M10 让 cid 形态从"偶然不匹配"变成"结构性不匹配"，真机验收会一直显示"旧版✗"。
