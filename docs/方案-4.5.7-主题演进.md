> 状态：**方案稿，未实现**。需过 CRA 后再动代码。
> 触发：用户提问「主题恒定不变，是不是对于长久的使用来说不太好？」→ 确认要 1(rename API) + 2(卫生节) + 3(体检指标)。

## 1. 现状核查（已实测）

| 操作 | API | dream 权限 | 说明 |
|---|---|---|---|
| 合并 | `mergeTopics`（`memory-store.mjs:1729`） | `merge:false`，走 `memory_review_topic` 专用工具 | **已正确处理名字**：源主题 name + aliases 全部并入目标 aliases（`:1758-1764`），源转 archived + 写归档指针 `merge_into:<dst>` |
| 拆分 | `splitTopic`（`:1816`） | `split:false`，走 `memory_split_topic` | 句子移到新主题，名字可指定（默认 `· 明细 N`） |
| 删除 | `deleteTopic`（`:1885`） | `delete:false` | 有 API 但 dream 不可直调 |
| **改名** | ❌ **无** | — | **唯一缺失的结构操作** |

真机数据：592 主题（active 214 / dormant 308 / draft 44 / archived 26）。

**已实证的重复问题**：trigger `memory_dream_patch` 同时挂在 T-0029 / T-0031 / T-0057 / T-0347 四个主题上。

## 2. 目标与非目标

**目标**
1. 补上 `renameTopic`，让"名字过时"可修
2. 让"主题卫生"成为 dream 的**常规动作**，而不是偶发
3. 让"该重构了"**可观测**（面板指标）

**非目标**
- ❌ 不做自动合并/自动改名（不可逆，必须 dream 判断 + 留痕）
- ❌ 不改三层结构（域→项目线→明细）本身
- ❌ 不动 `ARCHIVABLE_STATES` / lifecycle 语义

## 3. 改动

### ① `renameTopic`（`memtopic/src/memory-store.mjs`）

```js
renameTopic(topicRef, newName, { actor = 'runtime', reason = '' } = {})
```

**必须做的六件事**：
1. `can(actor, 'rename')` 权限校验（**新增权限位** `rename`，见 §4）
2. 新名 `normalizeName` 后**冲突检测**：
   - 与现有主题 norm 相同 ⇒ 拒绝 `NAME_CONFLICT`，提示「应走 merge 而不是 rename」
   - 与该主题自己的 aliases 冲突 ⇒ 允许（就是改名回来）
3. 更新 `name` + 重算 `norm`
4. **旧名进 `aliases`**（关键：保证旧名检索仍命中，符合"原文永不丢"）
5. 审计 `topic.rename`（记 `from` / `to` / `reason`）
6. **导出视图同步**：触发该主题的 md 导出重建（`projects|knowledge|sessions|tools/*.md`）

**不做**：不改 `id`（id 是稳定引用，`session_search` 指针、审计都依赖它）。

### ② dream 任务书「主题卫生」节

在现有「候选主题」块后新增一节，要求 dream **每轮顺手检查**（不是每次都动手）：

```md
## 主题卫生（每轮顺手检查，有问题才动手）
对候选主题逐个判断，只在**明确有问题**时处理：
- **近重复**：两个主题讲同一件事（名字/trigger 高度重叠）⇒ memory_review_topic({verdict:"merge", into:<保留的>})
- **命名过时**：主题名指向已不存在/已改名的项目 ⇒ renameTopic 或 memory_dream_patch 的 file 层修正
- **碎片**：正文 <3 句且无独立价值 ⇒ 建议合并进相关主题
- **超限**：>40000 字符 ⇒ memory_split_topic 按语义分片
纪律：**宁可不动，不要瞎动**；每次最多处理 3 个；每次操作必须在最终文本里报告「改了什么、为什么」。
```

### ③ 主题体检指标（面板 + `memory_topics`）

新增五个指标（只读，进「账本口径」卡）：

| 指标 | 定义 | 现有值（真机） |
|---|---|---|
| `dupTriggers` | 一个 trigger 挂在 ≥2 个 **active** 主题上的数量 | 待测（已知至少 1 组） |
| `fragments` | active 且 live 句数 <3 的主题数 | 待测 |
| `orphans` | 无 parent 且**非系统主题**的 detail 数 | 0（4.5.6 刚修口径） |
| `nearDupPairs` | 归一化名互相包含 / trigger 重叠 ≥2 的 active 主题对数 | 待测 |
| `oversized` | live 字符 >40000 的 active 主题数 | 2（T-0474/0475 是索引类，上限 200K，需排除） |

面板显示：`主题卫生：重复 trigger N · 碎片 N · 近重复 N 对 · 超限 N`；全 0 时显示「主题卫生：良好」。

## 4. 权限矩阵变更

`memtopic/src/governance.mjs`：

```js
// 新增 rename 权限位
runtime:  { ..., rename: true  }
dream:    { ..., rename: true  }   // 经专用工具，不直调 store
lead:     { ..., rename: true  }
user:     { ..., rename: true  }
archive:  { ..., rename: false }
```

**理由**：改名是**可逆**操作（旧名进 aliases，随时可改回），风险远低于 merge/delete，可以放开给 dream。

## 5. 三者交互（用户特别要求考虑）

| 场景 | 行为 |
|---|---|
| **先 rename 再 merge** | 源主题的当前名 + 历史 aliases 全部并入目标 aliases（`mergeTopics` 已实现，无需改） |
| **先 merge 再 rename** | 目标改名后，源名仍在 aliases 里 ⇒ 旧检索仍命中；新名成为主名 |
| **split 后 rename** | 新主题可独立改名；拆出的指针句记录原主题 id（不受改名影响，id 稳定） |
| **rename 撞名** | 拒绝，提示走 merge —— 因为"两个主题同名"本质就是该合并 |
| **rename 后导出视图** | 必须重建，否则 md 里还是旧名（导出视图是只读投影，重建即可） |
| **rename 后 trigger** | **不动** trigger（trigger 是检索入口，改了会丢召回）；如需改走 `addTrigger`/`retireTrigger` |

## 7. CRA 必审点

1. **`norm` 与去重的关系**：rename 后 `norm` 变了，`topicDbSearchTopics` / `detect` 的归一化匹配会不会受影响？导入期的近重复判定呢？
2. **aliases 膨胀**：反复改名会不会让 aliases 无限增长？要不要设上限（如 10 个）？
3. **导出视图重建的时机**：rename 立即重建 vs 等下一轮导出？立即重建会不会拖慢 dream？
4. **rename 权限放开给 dream 的风险**：会不会被用来"绕过 merge"（改成同名被拒，但改成相似名可以）？
5. **体检指标的性能**：五个指标要扫全库 592 主题，成本多少？要不要缓存/低频？
6. **`nearDupPairs` 的判定算法**：归一化名包含关系够不够？要不要加 trigger 重叠？会不会误报（如"项目"vs"项目管理"）？
7. **与 4.5.6 笔记归档的交互**：renamed 主题若变成笔记主题名？笔记主题应禁止 rename（它们是系统生成名）。
