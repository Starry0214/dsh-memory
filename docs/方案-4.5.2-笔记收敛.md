## 1. 结论摘要

笔记主题现在 append-only，dream 提炼后只追加「已提炼 → T-xxxx」，正文永不删 ⇒ 无限增长
（真机最大 67 句）；且代码不按 marker 过滤候选 ⇒ 已提炼主题每轮重复进 dream。

改为：dream 只产出「该主题已提炼完 + 指针文本」，**由插件执行整主题收敛**——追加指针行、
再删掉"收敛前那一刻存在的旧句"，最后校验只剩 1 行。新增句天然幸存。

## 3. 目标 / 非目标

**目标**
1. 笔记主题收敛成 1 行指针，可回溯。
2. 「未提炼」可观测（面板 / dream 任务书 / `memory_topics`）。
3. 已提炼主题不再重复进 dream 候选。

**非目标**
- 不做「没写 note 的会话」兜底队列（对齐 MiMo：原文在 session log，靠 `session_search`）。
- 不在 checkpoint 事件清笔记（我们的 checkpoint 主题不吸收笔记，清了就丢）。
- 不改 `memory_note` 的 append 语义。

## 5. 核心算法（P1-2）

```
noteTopicCompact(store, topicId, pointer):
  1. rows = store.readTopic(topicId).sentences
     ids  = rows.map(r => r.id)            // ★ 收敛前那一刻的旧句 id 全集
  2. if (!ids.length) return { skipped: "empty" }
  3. store.appendSentence({ topic: topicId, text: pointer, actor: "runtime" })
     → 指针行先落地（中断也不丢内容）
  4. for (id of ids) store.deleteSentence(topicId, { sentenceId: id }, { actor: "runtime" })
  5. 校验：readTopic(topicId).sentences.length === 1 且首行 == pointer
     - 不等 ⇒ monitorEvent("intent", "note-compact-verify-fail …")，不回滚（旧句已删但指针在，内容仍可 session_search）
  6. monitorEvent("intent", "note-compact ok topic=… removed=N")
```

**为什么不需要 CAS、也不需要 read 侧扩 id**
- `ids` 是插件在**收敛前一刻**自己读的，不是 dream 报的 ⇒ 无"dream 读到 N 但实际已变"问题
- 步骤 3 之后主 agent 再 append 的句子 id 不在 `ids` 里 ⇒ **必然幸存**
- 步骤 1 与 3 之间主 agent append 的句子同理幸存
- 中断安全：先加指针后删旧句，最坏结果是"指针 + 旧句并存"，不丢内容

**幂等**：若主题只剩 1 行且就是指针 ⇒ 直接 skip。

## 6. 并发与失败

| 场景 | 处理 |
|---|---|
| 主 agent 在收敛过程中 append | id 不在 `ids` 里 ⇒ 幸存（见 §5） |
| 两轮 dream 并发收敛同一主题 | 内存 per-topic 锁（Map+时间戳，同 `PLUGIN_SUBAGENT_SIDS` 手法）；未拿到锁 ⇒ skip |
| 步骤 4 中途失败 | 步骤 5 校验不过 ⇒ 留痕；指针已在，内容可通过 session_search 回溯 |
| 主题被删/改名 | 步骤 1 取不到 ⇒ skip + 留痕 |

## 10. CRA 必审点

1. **整主题收敛的原子性**：先加指针后删旧句的顺序，中断时会不会出现"指针 + 旧句"导致重复计数/重复提炼？
2. **id 捕获的时序**：`readTopic` 与 `appendSentence` 之间是否真的无其他写者插入（SQLite 单写者假设）。
3. **marker 语义迁移**：旧 marker 与新指针行共存期，`P0-1` 的过滤判据怎么写才不误判。
4. **P0-1 过滤的副作用**：会不会把"部分提炼"的主题也过滤掉（导致剩余内容永不再被提炼）。
5. **P2-1 归档出口**：会不会把还有用的笔记藏起来。

# §12 CRA 修订（v2）— 2026-11-06

> CRA 报告：`docs/audit/452-note-compact_CRA_2026-11-06.md`，判断「修了再开工」。
> **本节覆盖 §5 / §6 / §8 的相应部分**，其余章节不变。

## 12.1 致命缺陷与修订

### C1 · 收敛边界取错（原 §5 步骤 1）

**问题**：原方案在"收敛时"才读旧句 id 全集。但 dream 是后台子代理，跑数分钟；这期间主 agent
新写的 note 会进入 `ids` 被**误删**（真机 T-0560 有 43 句在上次 marker 之后）。

**修订**：**快照先行**。

```
dream 启动前（插件侧，每候选笔记主题）：
  snapshot[topicId] = { maxSentenceId: max(当前所有句 id), count }
dream 返回 {topic, pointer} 后：
  只删 id <= snapshot[topicId].maxSentenceId 的句子
  ⇒ 快照后新增的句子 id 更大，必然幸存
```

依赖：`sentences.id` 单调递增（SQLite 自增，成立）。

### C2 · `done` 全靠模型自报（原 §5 / §P1-1）

**问题**：B 版没定义 dream→插件的传输通道，`done` 是模型自报；**幻觉 done 但没写长期库 = 插件照删 = 不可逆丢内容**。

**修订**：删除前必须过**代码级验证**，任一不过则不删（退化为"只追加 marker"= 现状）：

| 验证 | 判据 |
|---|---|
| V1 本轮确实写过长期库 | `DREAM_WRITTEN_TOPICS` 非空，或本轮 `memory_dream_patch` 成功次数 ≥1 |
| V2 指针指向的目标真实存在 | 从 pointer 里抽出 `T-\d+`，`store.topics()` 里必须存在 |
| V3 主题未被并发收敛 | `snapshot[topicId]` 仍存在且未被消费（消费即删，防重放） |
| V4 快照内确实有内容 | `snapshot.count > 0` |

**传输通道**：不扩 `memory_dream_patch` schema。dream 在任务书里按固定 JSON 段落输出
`{"compact":[{"topic":"…","pointer":"…","targets":["T-0451"]}]}`，插件从**子代理最终文本**里解析
（与现有 dream 产出解析同源）。解析失败 ⇒ 不收敛。

### C3 · 迁移会误伤「部分提炼」主题（原 §8）

**问题**：`appendSentence` 只能追加，把指针挪到末尾 ⇒ 部分提炼主题被误判为"已提炼完" ⇒ 剩余内容永不再提炼。

**修订**：迁移**只处理「最后一句就是 marker」的主题**（真机 7 个），其余**原样不动**：

```
for each 笔记主题:
  rows = readTopic
  if (!rows.length) continue
  if (最后一句不是「已提炼 →」) continue      // 部分提炼 / 未提炼 ⇒ 跳过
  → 该主题本身就是"已提炼完"，把 marker 就地改写成新指针格式（replace 单句，不增不减）
```

## 13.1 四个 critical

### C1' · 判据不统一 ⇒ 首轮收敛后主题重新进 dream

**问题**：指针格式（M4 定的"日期开头"）与 P0-1/M3 的「最后一句是 marker」判据不一致，没有统一的
`isNotePointer()` ⇒ 收敛后的主题被当成"未提炼"，重新进候选 → 重复提炼 / 指针自指。

**修订**：定义**唯一判据**，所有地方（P0-1 过滤、统计口径、幂等 skip）都用它：

```js
const NOTE_POINTER_RE = /^\d{4}-\d{2}-\d{2} 已提炼 \d+ 句 → T-\d+/;
function isNotePointer(text) { return NOTE_POINTER_RE.test(String(text || "")); }
// 主题「已提炼完」的判据（唯一）：
//   rows.length > 0 && isNotePointer(rows[rows.length - 1].text)
//   —— 只看最后一句，不看"有没有 marker"（后者会误杀部分提炼主题）
```

`memory_note` 的 `endsWith` 去重、`memory_read` 渲染、面板统计全部复用该函数。

### C2' · V1 过松 ⇒ 幻觉 done 仍可删

**问题**：`DREAM_WRITTEN_TOPICS` 只要任意主题写/删一次就通过（含 delete/split/review），**无 per-target 校验**。

**修订**：删前对**指针里声明的每一个 target**逐个校验：

```
spawn 前快照：snapshotTargets = { "T-xxxx" → { writeCount, updatedAt, state, createdAt } }
           （对当时已存在的全部主题；不存在的新主题由 createdAt 判）

dream 返回后，对 compact[].targets 的每个 T-id：
  T1  若 spawn 前存在：writeCount 必须增长，且 state !== 'archived'
  T2  若 spawn 前不存在：createdAt 必须 > spawnTime（本轮新建）
  T3  target 主题名不得以 '笔记·' 开头（禁止指针指向笔记主题）
  T4  至少一个 target 通过（全不过 ⇒ 不收敛）
任一不过 ⇒ 不收敛、不写 marker、留 pending 待重试
```

### C3' · 迁移只 replace 不删旧句 ⇒ 旧句永不清

**问题**：v2 写"不增不减"，但 7 个主题的 marker 之前还有旧句；它们被 P0-1 过滤后**永远不会再被提炼**，
也不会被清掉。

**修订**：迁移时**删 marker 之前的所有句** + marker 就地改写为指针（同一事务）：

```
for each 主题:
  rows = readTopic
  if (!rows.length || !isLastSentenceMarker(rows)) continue   // 只处理"最后一句是 marker"
  idsBefore = rows.slice(0, -1).map(r => r.id)               // marker 之前的旧句
  事务 { 删 idsBefore → 把 marker 句 replace 成 isNotePointer 格式 }
  marker 在末尾 ⇒ 无重排风险
```

### C4' · 失败回退"只追加 marker"危险

**问题**：假 marker 会让 P0-1 跳过尚未提炼的内容 ⇒ 内容永久沉默。

**修订**：
- 失败时 **不写任何 marker、不收敛**，只留 pending 记录 + monitor 留痕，下一轮重试
- **禁止 dream 对笔记主题做 patch 写/删**：`memory_dream_patch` 校验加一条 —— topic 名以 `笔记·`
  开头 ⇒ 拒绝 `append/edit/replace/delete`（笔记正文只能由插件内部收敛改）
