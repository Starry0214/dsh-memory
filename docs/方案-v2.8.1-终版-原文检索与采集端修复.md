## §2 P0：采集端缺陷修复

### §2.1 事实（已实测定位，全部 file:line）

函数：`extractMessageFlowAsync`（`index.js:3149`），归档管道**唯一**的日志读取者。

**BUG-2｜`parts` 数组类型混装（纯代码缺陷）**

```js
// L3187：非 FULL 模式把**纯字符串**标记塞进 parts
if (!FULL) parts.push(si === 0 ? "[采样视图 " + nSel + "/" + frames.length + " 帧·首尾保真中段均匀]" : "[段 " + (si + 1) + "/" + nSel + "]");
// L3203/3210/3215：真实内容塞的是**对象**
parts.push({ si: si, s: piece });
// L3229：装配时按对象取 .s
const joinParts = (arr) => arr.map((p) => p.s).join("\n");
// L3241：空判定用长度
if (parts.length === 0) return null;
```

对**字符串**取 `.s` 得 `undefined`，`join` 把 `undefined` 渲染为**空串**。两个后果：

1. **标记行全部消失** —— 本意是告诉子代理"这是采样视图"，**实际一个字都没输出**（第二重静默谎言）。
2. **L3241 的空守卫被架空** —— 本该 `return null`（"没提取到内容"）的情形，被 18 个标记行撑成"非空"，于是返回一个**非 null 的空产物**。

**逐字符铁证**：会话 `60e0713f`（24860 帧）与 `da1a1bf8`（19892 帧）的单元 `chars = 17`，`text` 逐字为 **17 个 `\n`**。
来历：**18 个选中帧 → 18 个标记（全 string）→ 全渲染空 → `join("\n")` 得 17 个分隔符**。

**BUG-1｜`K` 的量纲错（设计缺陷）**

```js
const FULL = sizeMB < 8 || frames.length <= 12;          // L3158
selected = frames.slice(0, 2);                            // L3162
const span = Math.max(1, frames.length - 4);              // L3163
const K = Math.min(Math.max(6, Math.round(sizeMB * 1.5)), span);   // L3164 ← 量纲错
```

- `K` 按**文件大小**线性增长（**1.5 帧/MB**）
- 帧数按大小增长 **≈2700 帧/MB**
- ⇒ 选中占比随大小**急剧衰减**：9 MB → **18/24860 = 0.072%**；27 MB → 35/38355 = 0.091%
- 可归档事件（user/assistant/tool-call）只占少数帧 ⇒ **18 帧常常一个都没有**

**实测复刻（同一套选帧+抽取逻辑跑两遍，现行 vs 全帧）**

| sid | 日志MB | 总帧 | K | 选中帧 | 选中占比 | 现行产出 | **全帧产出** | 单元实际 |
|---|---|---|---|---|---|---|---|---|
| `2fa324f5` | 11.15 | 5255 | 17 | 21 | 0.400% | 1,675 | **200,011** | 1,703 |
| `328de10d` | 9.12 | 26103 | 14 | 18 | 0.069% | 333 | **164,570** | 394 |
| `60e0713f` | 9.06 | 24860 | 14 | 18 | 0.072% | 0 | **200,021** | **17** |
| `ad46e88c` | 26.93 | 38355 | 40 | 35 | 0.091% | 169 | **200,314** | 8,290 |
| `da1a1bf8` | 9.26 | 19892 | 14 | 18 | 0.090% | 0 | **129,176** | **17** |

**全帧产出全部顶到 `maxChars=200000`（装得满），现行产出 0–1,675 ⇒ 差 60 倍到 ∞。**
（我的复刻产出 0 而单元实际 17，差额正是 BUG-2 的指纹 ⇒ 定位自洽。）

**影响面（177 个单元全量实测）**

| 桶 | 会话数 | 保留率 | 字面量召回 |
|---|---|---|---|
| < 2 MB | 136 | 17.74% | 14.6% |
| 2~5 MB | 27 | 5.65% | 7.7% |

**阈值之上 vs 之下 = 29.8 倍落差。** 全集：**总保留率 9.01%、中位 17.49%、最低 0.005%；精确字面量召回 12.2%**（文件名 10.2% / GUID 5.5% / URL 13.0% / 文号 8.8% / HEX64 7.4%）。

### §2.2 BUG-2 修法（必做）

1. 标记行改**对象形态**，与真实 piece 同构：
   ```js
   if (!FULL) parts.push({ si: si, s: si === 0 ? "[采样视图 …]" : "[段 " + (si + 1) + "/" + nSel + "]" });
   ```
2. **空守卫改判"含真实内容的 piece 数"**，而非 `parts.length`：
   ```js
   const realPieces = parts.filter((p) => p && p.kind !== "marker");   // 标记与内容显式区分
   if (realPieces.length === 0) return null;
   ```
   ⇒ 建议给 piece 加 `kind` 字段（`"marker" | "user" | "assistant" | "tool" | "compaction"`），**下游计数与丢弃账本都靠它**（对齐 §3.2 的"丢弃必须显式计数"）。
3. `joinParts` 改为**只接收对象数组**并加运行时断言（`p && typeof p.s === "string"`），类型混装今后**当场抛出而非静默变空**。

### §2.3 BUG-1 修法（必做，两步）

**第一层（量纲修正，小改）**：`K` 按**帧数**缩放，不再按 MB：
```js
const K = Math.min(Math.max(6, Math.round(frames.length * 0.005)), 400);   // 0.5%，上限 400
```
预期：9 MB/24860 帧 → K=124、选中 ~128 帧（比 18 帧多 7 倍），27 MB/38355 帧 → K=192。

**第二层（根治，推荐）**：**按内容选帧**——不再按帧位置均匀采样，而是**只抽含可归档事件的帧**：

1. 第一遍流式扫帧（逐帧解压即弃，**不累积**），用 `line.indexOf('"type":"user/message"')` 等快筛（与现行同样的字符串快筛，无需 JSON.parse）记录**含内容的帧号**；
2. 第二遍对**这些帧**按预算提取。

- 收益：采样从"按位置猜"变成"**按内容取**"，`FULL` 阈值（8 MB）**可以彻底取消**
- 成本：多一遍解码（实测 0.172 s/MB ⇒ 27 MB 约 4.6 s；归档是后台轮次，可接受）
- **保留 `FULL` 快速路径**：小会话（< 8 MB 或 ≤12 帧）仍走单遍全量，避免无谓第二遍

**⚠ 内存纪律（硬约束，见 §3.9）**：两遍都要**逐帧即弃**，禁止 `Buffer.concat`。实测同一 27.27 MB 日志：concat 路径 maxRSS **922.9 MB**，逐帧即弃 **211.5 MB**。

### §2.4 顺带修（同函数，低风险，可选）

`L3237-3239` 的 compaction 分支是 `slice(-maxChars)`（**保尾**），而分段分支是保头——同一函数两条路径截断方向相反。批0 已加可见标记，本次**只补一句注释说明方向差异的意图**，不改行为（避免扩大改动面）。

## §3 P1：原文检索 CLI

### §3.1 布局

```
~/.dsh/tools/session-search/
├── session-search.mjs        # 构建 + 检索 + show + replay（单文件，零依赖，仅 node:fs/node:zlib）
└── README.md                 # 用法 + 口径 + ↓风险声明（首行）
~/.dsh/session-text/          # 缓存（与 memory 平级，不隶属）
└── <sid归属日 YYYY-MM-DD>/<完整uuid>/
    ├── manifest.json         # 唯一可变点，原子替换
    └── seg-0001.jsonl        # 写一次、永不修改
```

- **不注册为插件工具**时也用同一份脚本；P2 只加一层工具包装（§4）
- 缓存**不放** `~/.dsh/memory/`：否则被 `scanUndeposited`（`L1545`）/检索候选集/面板统计/预算告警扫到

### §3.2 收录口径（契约）

| 事件类型 | 收 | 抽取路径 |
|---|---|---|
| `user/message` | ✅ | `data.content[]` 中 `type==="text"` 的 `c.text` |
| `assistant/message` | ✅ | `data.message.content[]` 中 **`filter(c => c.type === "text")`** 的 `c.text` |
| `system/message` | ✅ | 同 `assistant/message` 路径 |
| `tool/call` | ✅ | `data.name` + `data.arguments` |
| `tool/result` | **仅错误** | 见下方判据 |
| `compaction/summary` | ✅ | `data.summary[]` 中 `type==="text"` 的 `c.text` |
| `assistant/chunk` / `text-chunks` / `reasoning-chunks` / `tool-call-chunks` | ❌ | 流式增量块（实为 token `dt` 数组 / 块边界事件） |
| `request/header` | ❌ | 请求配置头 |
| 其余控制事件 | ❌ | — |

**三处必须写死的细节（实测裁决，勿凭直觉）：**

1. **错误判据 = `content[].isError === true`**（**不是** `data.error`，**不是**字符串嗅探）。
   实测：132 例上 `data.error` / `content[].isError` / 文本嗅探三者等价（各 15）；**跨 18 个日志另查出 3 例 `isError:true` 而 `data.error === undefined`**（正文均为 `Error: sandbox escalation to …`，内层 `run_code` 失败）。⇒ **`content[].isError` 是超集**；可写 `A ∨ B`，**绝不可只用 A**。
2. **`assistant/message` 必须 `filter(type==="text")`**：`reasoning` 块**也带 `text` 字段**，naive `map(c => c.text)` 会**吞进 reasoning 全文**（与"不收 reasoning"自相矛盾且体积暴涨）。实测 48 条 assistant/message 中 **12 条（25%）没有任何 text 块** ⇒ 需**单独计数打印"类内空正文"**。
3. **`assistant/message` 的正文在 `data.message.content[]`**（`data.content` 路径 0 命中）；**`user/message` 的正文在 `data.content[]`**（无 `message` 层）。两者路径不同。
4. **`compaction/summary` 无实测覆盖**（两席样本均 0 条）⇒ **门必须专门造夹具**。

**丢弃必须分类计数并打印**（`丢弃 <kind>=<行数>`），否则就是下一个"静默丢"。长期指标而非一次性打印。

### §3.3 缓存行格式

```json
{"k":"_meta","ver":1,"sid":"<完整uuid>","files":["session.jsonl.zstd","session.v3.jsonl.zstd"],"built":"…"}
{"t":1789006838082,"k":"user/message","s":9,"f":"session.jsonl.zstd","x":"…逐字正文…"}
```

- **一行一事件** ⇒ 行号即事件级定位
- 换行**交给 `JSON.stringify` 单次编码**（`\n`），**禁止手工二次转义**（唯一逆变换）
- `x` **逐字**，不截断、不改写、不脱敏
- `f` 标注来自哪个物理文件（劈开会话必须可分辨）
- `s` = **源帧序号**（仅供溯源，**不是**缓存行号）

### §3.4 身份键与归并（劈开会话）

- 一个 sid 收其目录下**全部** `.zstd`（**不是** `SESSION_LOG_CANDIDATES` 两个名字——否则 DSH 再改名成 v4 会**静默漏收第三个文件**）
- **身份校验**：逐个文件解码帧 0，其 `session` 头 `session.id` 必须等于目录 sid；相符即并入，不符则**报告不静默**
- **主排序键 = `(文件序, 文件内帧序, 帧内行序)`**（必然存在）；**`time` 降级为展示 + overlap 校验**（chunk 类只有 `time0`、`session` 头只有 `createdAt`，`time` 不是普适键）
- 两文件 `time` 区间重叠 → **报 `overlap` 警告**，不静默按文件序拼

**实测依据**：7 个 sid 被 09-10 改名劈成两文件（已 7/7 证实同 `session.id`、**seq 双从 0 重开**、mtime 不重叠），合计 150.2 M 字符中 **41.0 M 对插件不可见**。

### §3.5 水位与增量

`manifest.json` 每文件记录：`{ name, size, frames, byteOffsetConsumed, frameDigest, chars }`

- **水位 = 源文件 + 已消费字节偏移 + 该处帧的解压内容摘要**（**不是帧计数**：伪 magic/坏帧/扫描器版本变化会让"第 k 帧"错位 ⇒ 续跑静默跳段或重放）
- 帧数只作 sanity check
- 文件变大 → 追加新段；文件变小/摘要不符 → 全量重建
- **永久残帧**：进程被杀会在尾部留下**永远不会被写完**的残帧（后续 append 从其后开始）⇒ 与"坏帧只丢该帧 + 记账"配套；**"半截帧下次补回来"只在宿主继续写完该帧时成立**

### §3.6 原子性与并发

- **段文件写一次永不修改**（`seg-NNNN.jsonl`）；**`manifest.json` 是唯一可变点**，`tmp → rename` 原子替换
- **本方案不用"增量 = 重写整档"**：那会变成"只省 CPU 不省 I/O"（最大 sid 实测 60.1 M 字符 ≈ 80 MB，每次查询前白重写一遍）
- **并发**：两进程同构建同一 sid → 无重复行、manifest 条目完整；查询与构建并发 → 读者只看到完整文件
- **Windows 风险**：`rename` 撞上正在读该文件的 `rg` 可能 `EPERM/EBUSY` → 需重试退避，且**测试必须覆盖此场景**

### §3.7 检索与输出（两个 P0 级不变量）

**不变量 A：坐标必须属源侧坐标系，或显式标注**
缓存行号会随口径版本重建**整体漂移**，外存下来的引用静默腐烂。⇒
- 输出**每一处坐标带标签**：`cache:#1204` / `src:<file>#f12@0x1A3C`
- `--show` **接受源坐标**（sid + 源文件名 + 帧号/字节偏移），由 `f`+`s` 还原
- 缓存行号**只许用于同一次调用内的二次访问**

**不变量 B：截断绝不冒充命中数**
rg 是**行序**不是相关度序，`--limit` 只是"遍历到的前 N 条"——最相关的可能落在 limit 之外 ⇒ **不报错、有结果、结果都是真的** ⇒ 用户读成"原文里没这句"（**静默假阴性**）。⇒
- **先 `rg --count` 拿总数**
- **永远打印「命中 N 处（其中列出 M 条）」**
- **绝不把截断后的条数当命中数**

**零结果引导**（照抄 mimocode 语义，不照抄文案）：显式声明「**0 结果 ≠ 没记录**」，给出 ①换更稀有的词（精确 ID/路径/编号 优于描述性长句）②放宽 `--since`/去掉 `--kind` ③缓存可能滞后，先跑增量。

**依赖缺失**：`rg` **实测不在 PATH**（二进制在 `@deepseek-ai/dsh/node_modules/@vscode/ripgrep-win32-x64/bin/rg.exe`）⇒ 工具必须**自行定位**，且缺失时**显式报错 + 非零退出**，**绝不报 0 命中**。

### §3.8 `--replay`（第二个入口，可能更常用）

```
session-search.mjs --replay --since 2026-09-15 --until 2026-09-15
```
- 只列 `user/message`（全库仅 ~2.7%、约 5000 万字符），按时间铺出
- **适用"依稀记得但想不起词"**：人记得的是**场景**不是词；回放不依赖猜对关键词
- 成本：一天的会话用户消息可能仅几十 KB

### §3.9 内存纪律（写进代码注释的门）

1. **逐帧解码即弃**，禁 `Buffer.concat`（实测 27.27 MB 日志：concat maxRSS **922.9 MB** vs 逐帧 **211.5 MB**）
2. 逐帧/逐行 `fs.writeSync` 直写，不累积大字符串
3. **检索在进程外**（rg 子进程）；脚本**永不把语料读进内存**（全库正文 124–149 M 字符，进 JS 是 UTF-16 ⇒ **248–298 MB 堆常驻**且挂宿主）
4. 一次只处理一个 sid（峰值由最大单文件决定：实测规律 ≈ `max(57 MB, 6.9 × 单文件MB)`）

## §5 验证门（R1–R18 + Variant 仪式）

**前置**：工具必须支持 **root 覆盖**（`DSH_HOME` / `--sessions-root` / `--cache-dir`），否则门只能污染真库（713 MB / 全量 123 s）。

**鉴别仪式（Variant 仪式）**：本方案是全新工具，**没有"上一版字节"可比**。⇒ 工具内置隐藏开关 `SELFTEST_BUG=<id>`，门在每种变体下**必须红在指定编号**，门头写死 `id→门` 映射。**没有这个开关，FAIL 形态无法演示 ⇒ 门等于没被证明过。**

| # | 断言要点 | FAIL 形态（必须让它红的变体） |
|---|---|---|
| **R1** 幂等 | 连跑两次：**全文件**（`.jsonl` + `manifest.json`）sha256+mtime 不变、报 0 变更；追加一帧后同样 0 变更 | `touch-every-run`（`builtAt` 只在**真写入**时更新） |
| **R2** 增量==全量 | 两个独立目录、**两次子进程**：`sha256(INC) === sha256(FULL)` 逐字节；`INC` 前 N 行与 `S0` 前 N 行逐字节相同；**且 `INC ≠ S0`**；**并断言"本次实际解码帧数 < 文件总帧数"** | `no-incremental` |
| **R3** 守恒 | 门**独立**逐帧解原日志、按 KEEP 自行计数 → == 缓存行数；丢弃按**类型**打印且逐类求和 == 独立算出的未保留数 | `drop-system`（丢 `system/message`）、"丢弃=总数−保留"的同义反复 |
| **R4** 逐字 | 确定性抽 ≥50 条（首/尾、`\n`、CRLF、引号反斜杠、emoji、超长行）：`unescape(x) === 原文` **且长度相等**；**缓存行数 === 事件数** | 截断 N 字符；转义丢字符；非法 UTF-8 抛/截行 |
| **R5** 劈开会话 | 合成夹具（同 `session.id` 两文件、seq 双从 0、mtime 不重叠）→ 两文件哨兵都在、`f` 可分辨、顺序=时间序；**重叠夹具 → 必须打 `overlap`** | `single-file`（用 `resolveSessionLogPath` 单文件版 ⇒ 旧名哨兵缺失） |
| **R6** 内存 | 门断言工具自报 `process.resourceUsage().maxRSS` < `基线(≈57 MB) + 6.9 × 单文件压缩大小`（合成夹具） | `concat` |
| **R7** 检索 | 合成语料（中文/含空格中文路径/文号/函数名）命中且 sid+行号+文件名**全对**；`--show` 回看逐字一致；**0 结果走引导分支**；**`rg` 缺失 → 非零退出，绝不报 0 命中** | `rg-missing-mode`、shell 拼接参数（空格路径即碎） |
| **R8** 污染 | ①源码：扫盘根只有 `sessions/`、`sessions/archive/`、`knowledge/`、`projects/`、`tools/`、ROOT_FILES，不含 `session-text` ②运行时：fixture 放哨兵 → 插件全部读路径输出**零哨兵**、`.monitor.json`/`.integrate.json` 零 `session-text` 字串 ③**反向对照**：同一哨兵复制进 `knowledge/` **必须出现** ④构建+查询后 `~/.dsh/memory/**` sha256 不变 | 缓存放 `memory/` 下；扫描根写成 `MEMORY_ROOT` 递归 |
| **R9** 残帧 | 截尾 → 不崩、缓存全行合法、字节偏移水位不含坏帧；补齐该帧后增量 → 哨兵**出现**；**且断言走的是增量**（`rebuilt:0, appended:1`） | `size-watermark`（坏帧永久丢）、总是全量重建（"补回来"恒真=假绿） |
| **R10** 口径版本 | 改 KEEP → 全量重建，且**被排除的 kind 零残留** | 只断言"重建发生" |
| **R11** 原子 | 中途 kill → 缓存要么无、要么完整版；`.tmp` 残留不被读；**覆盖"`rg` 正读该文件时 rename"**（Windows 可能 EPERM/EBUSY） | `inplace-write` |
| **R12** 并发 | 两进程同构建同 sid → 无重复行、manifest 条目完整；查询与构建并发 → 读者只看到完整文件 | manifest 读-改-写竞态（丢水位→重复消费→**重复行**） |
| **R13** 依赖缺失 | `rg` 不在 PATH → 显式报错 + 非零退出 | 返回 0 命中 |
| **R14** 编码 | 夹具写入 CP936/非法 UTF-8 字节 → **策略必须定义**（替换字符可接受，但**不得抛、不得截行**）；抓 stdout 原始字节断言合法 UTF-8 | — |
| **R15** 路径 | 临时目录名含**中文+空格+括号** → 构建/检索/`--show`/`rg` 参数全通 | — |
| **R16** 插件回归 | 若做 P0/P2：既有 9 个门全绿 + `decodeSessionLog` 行为门（末帧哨兵 + token 总量 oracle，防"只解第一帧"） | — |
| **R17** 可发现性 | `tools/会话原文检索.md` 存在且命令路径正确 | — |
| **R18** 运行账本 | `runs[]` 计数 + 查询日志（供"要试几轮"可测） | — |

**防"门全绿但功能是坏的"五条**：
1. 每条门必须有 `SELFTEST_BUG` 变体让它红，**否则删掉该门**
2. 断言一律在**合成夹具**上、门**自己独立复算**（R3 自己解帧、R2 自己 sha256、R4 自己 unescape）——**不采信工具自述的任何数字**
3. 每条"没发生"的断言配**反向对照**（R8 的 knowledge 哨兵必须出现；R9 必须证明走了增量；R2 必须 `INC ≠ S0`）
4. **两条正向能力门**（需求判据 1/2 各一条端到端），任何重构都必须让它们继续绿
5. 跑完打印"**变体 × 门**"矩阵，**缺格即拒收**

## §6 明确不做

| 不做 | 理由 |
|---|---|
| FTS5 / SQLite / 任何索引表 | rg 全形态实测 **0.25–0.62 s / 8–9 MB**（1066 文件 / 169.4 MB）。索引的唯一收益是速度，而速度已够 |
| 向量 / embedding / 语义检索 | mimocode 零向量；语料 16.98 亿字符。**且"关键词检索"的天花板是形态性的**——用户只剩纯语义印象时，任何词法检索都无能为力（含 mimocode） |
| **盖章（归档侧注入 sid）** | D1 裁决：主用例只需"拿前缀换全值"，前缀本身就够。留 P3 待估 |
| `--with-reasoning` | D4 裁决：破坏归并键 + 体积大 + mimocode 也不收 |
| 常驻 watcher | 违反"常驻内存 0"；按需增量已足够 |
| 脱敏 | 会毁掉逐字溯源（而逐字正是需求）⇒ 改为 D2 的三条隔离 |
| 留存策略 / 自动清理 | 成本可接受（~190 MB vs 713 MB 压缩日志）；给 `--rebuild` |
| 反向查漏报表（`scanUndeposited` 的 raw 版） | 是"分析报表"不是"检索"；且 P0 修完基线才干净 |
| **备份** | `runBackupNow` 只整树复制 `MEMORY_ROOT` ⇒ 本缓存**不会被备份**（**显式记录**，否则将来会问"备份里为什么没有它"） |

## §7 风险与缓解

| # | 风险 | 缓解 |
|---|---|---|
| R1 | **缓存滞后**：活跃会话最后几秒搜不到。滞后 = 上次构建 → 宿主最近一次 flush | 查询前先增量。**缺口三类**：**(a) 未 flush 的宿主机内缓冲——重跑永远拿不到（硬边界）**、**(b) 已 flush 但晚于上次构建——重跑可补**、**(c) 残帧/水位错位——重跑修不了**。README 必须如实写明，**否则 agent 会把"搜不到"读成"没记录"** |
| R2 | **明文副本不可撤**（含 token/SSO/客户数据） | D2 三条隔离 + README 首行声明。**不承诺"不读本机"** |
| R3 | 体积随日志线性增长 | 接受；给 `--rebuild` |
| R4 | **利用率**：记忆条目是摘要重写过的，可能 grep 不到原句 | ①`--replay` 兜底（不依赖猜词）②P0 修完字面量召回应显著上升 ③零结果引导必须写进工具的**返回文案**（不只 README） |
| R5 | P0 改动触及归档**唯一**读取者，回归面大 | 逐帧即弃 + 保留 FULL 快速路径；`_probe-archive-loss.mjs` 修前/修后对比；既有 9 门全绿 |
| R6 | `time` 归并依赖 `time` 存在 | 主键已改 `(文件,帧,行)`，`time` 仅展示 |
| R7 | 首次全量构建 ≈123 s + ~190 MB 写入 | 需用户知情；给 `--since` 先小范围 |
| R8 | 每次调用起进程 ~0.6 s | 接受 |
| R9 | P0 修复会**改变单元缓存基线** | 修后清空 `.archive-units/` 重跑（可重建派生物） |
