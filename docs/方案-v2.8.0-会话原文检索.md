## §0 需求（用户原话，逐字）

> 「有些内容在记忆中可能不准确或者没计入，那么就可以通过这个功能**直接就检索到来源**之类的」
>
> 「其实我要的功能需求很简单」
>
> 「这样子会不会太复杂了？**mimocode 应该就是一个检索功能吧**？」
>
> 「会不会占用很大的内存？」

**需求判据**（做完必须能演示）：
1. 给一条记忆里的说法（甚至只是半句字面量），能查到它**在原始对话里出现过没有、原话是什么、哪个会话哪一条**。
2. 能反向查：某个字面量在原文里出现过，但记忆库里没有。
3. 复杂度必须**低于或等于 mimocode**（用户明确反对再堆层次）。

**先定性质：这不是"给记忆插件加功能"，而是"给 agent 加一个检索入口"。** 本方案的默认形态**不改插件、不注册工具、不需重启**。

## §1 结论先行

做成**一个 CLI 命令**，构建与检索合一：

```
node ~/.dsh/tools/session-search/session-search.mjs <关键词> [--since 2026-09-01] [--sid abc123] [--kind user/message] [--limit 20]
```

内部三步：**① 增量构建**（只解变化过的日志）→ **② 用 ripgrep 搜纯文本缓存** → **③ 打印出处**（sid / 时间 / 事件类型 / 命中行 / 回看原文的命令）。

三条硬性技术选择，各有实测依据：

| 选择 | 依据 |
|---|---|
| **不上 FTS5 / 不上 SQLite / 不上向量** | 318 MB 语料 ripgrep 全扫 **0.08~0.17 秒**、峰值 **8~15 MB**。mimocode 要 FTS5 是因为它**没有**一个够快的全文扫描器；dsh 有 ripgrep。 |
| **缓存是磁盘纯文本，绝不读进宿主进程** | 全库正文 124 M 字符；进 JS 是 UTF-16 → **248 MB 堆常驻**且挂在宿主上。落盘则常驻 **0**。 |
| **逐帧解码即弃，不 concat** | 同一份 27.3 MB 日志：concat 峰值 **932 MB**（external 峰值 1541 MB）/ 11.7 s；逐帧即弃 **187 MB** / 4.7 s。**差 4.7 倍内存、2.5 倍时间。** |

## §2 现状事实（全部实测）

### §2.1 记忆检索现状 —— "溯源"这条链目前根本不存在

| 事实 | 值 |
|---|---|
| 记忆库 `[ses …]` 标记总数 | **616 处** |
| 其中**日期形**（`[ses 2026-09-15]`） | **616 处 = 100%** |
| 其中**会话 id 形**（`[ses <hex>]`） | **0 处**（全库 `\[ses [0-9a-f]{6,12}[,\]]` 零命中） |
| 日期指向的东西 | `sessions/2026-09-15.md` —— **它本身是摘要，不是来源** |
| 真来源的位置 | `~/.dsh/sessions/<slug>/<sid>/session[.v3].jsonl.zstd` |
| 一个工作目录一天的会话数 | **40+**（示例 slug `agent周事项-插件开发调整` 下即有约 40 个 sid 目录） |

> **结论：标注精度是"天"，而一天有几十个会话 —— 等于没有链接。** 现存 616 条标记对"回到来源"零帮助：只能拿日期 + 关键词去那一天的几十个日志里手工翻。
>
> 注：任务书 L8760 早已允许 `[ses <id>]` 形态（"追加 `[ses YYYY-MM-DD]` 或 `[ses <id>]`"），只是从未被使用。

### §2.2 原文层现状

| 事实 | 值 |
|---|---|
| 日志文件（精确名 `session.jsonl.zstd` / `session.v3.jsonl.zstd`） | **1073 个 / 713.2 MB** |
| 唯一 sid | **1066 个** |
| 目录命名 | `session-<uuid>` **300 个** / 裸 `<uuid>` **773 个** |
| 备份文件（`.bak-presetfix-*`）被计入？ | **否**（后缀不是 `.zstd`，精确名过滤天然排除） |
| 帧总数 | ≈ **1,445,774**（实测 85922 帧/27.3 MB） |

| 坏帧 / 非 JSON 行 | **0 / 0** |

#### ★ 一等事实：一个 sid 可能对应**两个**物理日志（7 例，已 7/7 证实）

DSH 于 **2026-09-10 20:10** 把日志改名 `session.jsonl.zstd` → `session.v3.jsonl.zstd`。**在该时刻仍存活**的 7 个会话，被劈成两个文件：

| sid | 旧名（早半段） | 新名（晚半段） |
|---|---|---|
| `ad46e88c` | 12.43 MB / 31407 帧 / 25.43 M 字符 | 14.50 MB / 6948 帧 / **60.10 M 字符** |
| `6c22526b` | 3.76 MB / 9838 帧 / 7.89 M | 1.60 MB / 216 帧 / 7.99 M |
| `7fbd82f9` | 2.14 MB / 5905 帧 / 3.23 M | 1.20 MB / 260 帧 / 4.06 M |
| `653e7d8a` | 0.80 MB / 2765 帧 / 1.37 M | 2.37 MB / 1104 帧 / 8.47 M |
| `b19314ee` | 1.44 MB / 3804 帧 / 3.07 M | 0.54 MB / 172 帧 / 2.98 M |
| `574b8af7` | 0.01 MB / 2 帧 / 0.01 M | 7.50 MB / 3747 帧 / 25.60 M |
| `28a52c6a` | 0.03 MB / 13 帧 / 0.03 M | 0.02 MB / 6 帧 / 0.04 M |
| **合计** | **≈ 41.0 M 字符** | **≈ 109.2 M 字符** |

证实手段（`_probe-split-sid.mjs`）：
- 两个文件的帧 0 **都是 `session` 头，且 `session.id` 完全相同** → 同一逻辑会话
- **两个文件的 seq 都从 0 重新开始** → **seq 不能用来拼接**
- 两文件的 mtime 时间上不重叠（旧名最后写 ≤ 09-10 20:10，新名创建 ≥ 09-10 20:10）

**两个直接后果：**
1. **插件今天读不到早半段。** `resolveSessionLogPath(dir)` 是"v3 优先、legacy 兜底"的**返回单文件**实现 → 对这类目录**只返回 v3**。7 个会话合计 **150.2 M 字符中有 41.0 M（27%）对插件的 漏网检测 / 帧数水位 / used 判定 / 归档提取 永久不可见**，且**零报错**（与批0 修的四条同型：静默丢）。
2. **任何"一 sid 一文件"的缓存构建器都会静默覆盖**：若按 sid 命名输出，晚半段会覆盖早半段。**这恰好会让本功能丧失可信度**——搜不到的会表现为"记忆里没记"，实际是"构建时被覆盖"。

### §2.3 mimocode 对照（源码在 `E:\工具\插件开发调整\mimo-src\MiMo-Code-main`）

用户判断正确：**它就是两个检索，没有第三样东西。**

| 项 | `memory` 工具 | `history` 工具 |
|---|---|---|
| 表 | `memory_fts(path, scope, scope_id, type, body, fingerprint)` | `history_fts(part_id, **session_id**, **message_id**, project_id, kind, tool_name, body, time_created)` |
| 语料 | 策展的记忆 .md | **原始对话消息** |
| 检索 | SQLite FTS5 `MATCH` + `bm25` + `snippet` | 同左 |
| 返回 | 路径 + snippet + 分数 | **sid + message_id + kind + snippet + 分数** |
| 加值 | — | `around(message_id, before, after)` → **取该消息前后各 5 条完整原文** |
| 向量 / embedding | **无** | **无** |

收录口径（`history/extract.ts` L11-16）：
```ts
DEFAULT_KINDS = ["user_text", "assistant_text", "tool_input", "tool_error"]
```
- **不含 `tool_output`** → 它不是全量索引
- 不含 `reasoning`

工具自身的零结果引导（`tool/memory.ts` L46-55，逐字）：
> "0 results does NOT mean it was never recorded. Escalate before giving up: … For VERBATIM recall of something a summary may have glossed over (exact command, the user's precise wording) — use the **history tool (raw conversation)**, which keeps original messages. **Widen scope progressively: session → project → global → history.**"

> **本方案 = 把 mimocode 的 `history` 表换成「磁盘纯文本 + ripgrep」。** 因为 dsh 没有消息表，原文是磁盘多帧 zstd；而一旦接受"检索在进程外"，索引这一层就是纯多余的。

### §2.4 内存与体积实测（回答"会不会占很大内存"）

**最大单日志（27.3 MB / 85922 帧 / 52.8 M 字符）**：

| 实现 | OS 峰值工作集 | external 峰值 | 耗时 |
|---|---|---|---|
| `Buffer.concat`（**插件现用的 `decodeSessionLog`**） | **932.4 MB** | **1541.6 MB** | 11.7 s |
| 逐帧即弃 | **198.0 MB** | 61.6 MB | 4.7 s |
| 逐帧即弃 + 直写磁盘（本方案） | **187.5 MB** | 56.5 MB | 6.8 s |

**缩放规律**：峰值 ≈ `max(57 MB, 6.9 × 单文件压缩大小)`，**只由最大的单个日志决定，不随全库累加**（1073 个文件挨个过）。
- 典型文件 0.4 MB → 77 MB；小文件 → 57 MB（node 基线）

**检索侧（ripgrep，语料 318 MB / 70 文件）**：

| 场景 | 峰值 | 耗时 |
|---|---|---|
| 无命中（全扫） | **8.3 MB** | 0.08 s |
| 罕见命中 | 8.4 MB | 0.09 s |
| 海量命中（截断输出） | **14.6 MB** | 0.17 s |
| 单文件 4.4 MB 对照 | 6.6 MB | — |

→ **内存不随语料增长**，只随命中条数（输出缓冲）小幅增长。

**常驻内存：0**（无索引库、无常驻进程、不搜时不占）。

**缓存体积投影**（30 文件跨尺寸分层抽样，与原解码字符比）：

| 项 | 值 |
|---|---|
| 保留正文 | **3.27 M 字符 / 4.37 MB**（UTF-8），4343 行 |
| 占原解码字符 | **6.7%**（最大单文件口径 7.2%，吻合） |
| 字节/字符 | 1.34 |
| **全库投影** | **≈ 124 M 字符 ≈ 166 MB 纯文本** |
| 一次性构建耗时 | ≈ **123 秒**（0.172 s/MB × 713 MB）；此后只重解变化的文件 |

## §3 设计

### §3.1 形态与放置

```
~/.dsh/tools/session-search/
├── session-search.mjs      # 构建 + 检索（单文件，零依赖，只用 node:fs / node:zlib）
└── README.md               # 用法 + 口径 + 回看原文方式
~/.dsh/session-text/        # ← 缓存目录（与 memory 平级，不隶属）
├── .meta.json              # 每个 sid 的构建水位 + 口径版本
└── <完整 uuid>.jsonl       # 一个 sid 一个文件
```

**为什么放 `~/.dsh/tools/` 而不是插件目录**：本工具不注册为插件工具、不被插件加载 → 放插件目录会被误认为插件的一部分，也会让"改了插件要重启"的心智负担平移过来。

**为什么缓存必须放 `~/.dsh/session-text/` 而不是 `~/.dsh/memory/` 下**：memory 目录被多条现有逻辑扫描，放进去会立刻污染：
- `scanUndeposited` 遍历 `sessions/` + `knowledge/` + `projects/` + `tools/` + 根文件
- 检索候选集（`memory_search`）
- 面板字符统计 / 预算告警 / `.stats-panel.html`

→ 缓存放在**平级新目录**，天然不在任何现有扫描面内（G8 门验证）。

### §3.2 收录口径（对齐 mimocode，本方案的**契约**）

| 事件类型 | 收 | 理由 |
|---|---|---|
| `user/message` | ✅ | 用户原话（最高价值，逐字） |
| `assistant/message` | ✅ | 助手成品消息（**抽 `content[].text`**，不含 tool_use 结构） |
| `system/message` | ✅ | 系统提示（体量很小） |
| `tool/call` | ✅ | 工具入参（= mimocode 的 `tool_input`） |
| `tool/result` | **仅错误行** | = mimocode 的 `tool_error`；**成功输出不收**（= mimocode 不收 `tool_output`） |
| `compaction/summary` | ✅ | 宿主压缩摘要（模型看全量后的浓缩） |
| `assistant/chunk` / `text-chunks` / `reasoning-chunks` / `tool-call-chunks` | ❌ | **流式增量块，与成品消息内容重复**；合计 **33.4%（≈6.1 亿字符）** |
| `request/header` | ❌ | 请求配置头，5.6% |
| `reasoning-chunks`（思考过程） | ❌ | mimocode 默认也不收；留 `--with-reasoning` 开关（默认关） |
| 其余控制事件（`step/*` `turn/*` `sandbox/mode` …） | ❌ | 无检索价值 |

**丢弃必须计数并打印**（`丢弃 <类型>=<行数>`），否则就是下一个"静默丢"。

### §3.3 缓存行格式（JSONL，一行一事件）

```
{"k":"_meta","ver":1,"sid":"<uuid>","files":["session.jsonl.zstd","session.v3.jsonl.zstd"],"built":"2026-09-18T…","src":"…"}
{"t":1789006838082,"k":"user/message","s":9,"f":"session.jsonl.zstd","x":"…正文（换行转义为 \\n）…"}
```

- **一行一事件** → ripgrep 的**行号 = 事件级定位**，`rg -n` 的输出直接可用
- `f` 字段 = 该事件来自哪个物理文件（§2.2 的劈开会话必须可分辨）
- `x` 是**逐字原文**，只做换行转义，**不改写、不截断、不脱敏**

### §3.4 多文件 sid 归并（§2.2 的直接对策）

一个 sid 收集其**目录下全部**候选日志文件（`SESSION_LOG_CANDIDATES` 两个名字，**不是** `resolveSessionLogPath` 的单文件版）。

- **归并键 = 事件 `time` 字段**（epoch ms），**不是 seq**（实测两个文件 seq 都从 0 重开）
- 无 `time` 的头事件（`session` 等）按文件顺序置前
- **不重叠假设必须被验证而非假定**：构建时若发现两文件时间区间重叠 → 报 `overlap` 警告，不静默处理
- 输出顺序 = 时间序 → 缓存文件可当"该会话的连续时间线"读

### §3.5 增量与失效

`.meta.json` 每 sid 记录：`{ ver, files: { <name>: { size, frames, consumedFrames, chars } }, builtAt }`

| 触发条件 | 动作 |
|---|---|
| 缓存不存在 | 全量构建 |
| `ver`（口径版本）≠ 当前 | **全量重建**（否则新旧口径混合 → 检索结果不可信） |
| 文件 size 未变 | 跳过 |
| 文件 size 变大 | **追加**新帧（日志是纯追加流） |
| 文件 size **变小** | 全量重建（异常，如被截断/替换） |
| 出现新的文件（旧名→新名新增） | 按 §3.4 归并后重建该 sid |

**水位记的是 `consumedFrames`（成功解出的帧数）而不是文件 size** —— 因为活跃会话的**末帧可能不完整**（正在写），`decompressFrameAt` 返回 null。只记 size 会让这半帧**永久丢失**。（批0 已确立"坏帧只丢该帧"的语义，这里要接上"下次补回来"。）

**原子性**：一律写 `<sid>.jsonl.tmp` → `rename` 覆盖。绝不原地追加写（否则并发检索会读到半截文件）。全量重建与增量追加都走同一个原子替换路径。

### §3.6 内存纪律（写进代码注释的门）

1. **逐帧解码即弃**：`for (const off of offs) { const b = decompressFrameAt(buf, off); … }`，**禁止** `Buffer.concat`
2. **逐帧/逐行 `fs.writeSync` 直写**，不累积大字符串
3. **检索在进程外**（ripgrep 子进程）；本脚本**永不把语料读进内存**
4. **一次只处理一个 sid**（峰值由最大单文件决定，不随全库累加）

### §3.7 输出形态

```
$ session-search.mjs 招标文件正文.pdf
命中 12 处（3 个会话）

[ad46e88c] 2026-09-10 18:22  tool/call          session.jsonl.zstd:1204
  …{"file_path":"…\\招标文件正文.pdf"…
[ad46e88c] 2026-09-14 20:31  user/message       session.v3.jsonl.zstd:88
  …那个招标文件正文.pdf 是 201 页…
[3c0d2d7d] 2026-09-15 09:12  assistant/message  session.v3.jsonl.zstd:341
  …《招标文件正文.pdf》…

回看原文：node ~/.dsh/tools/session-search/session-search.mjs --show ad46e88c --line 1204
```

- 出处三件套：**sid / 时间 / 物理文件名 + 行号**
- `--show <sid> --line N` → 打印该行完整正文 + 原始日志路径（必要时 `--raw` 直接给出 `~/.dsh/sessions/...` 路径供人肉查看）
- **零结果引导**（照抄 mimocode 的语义，不照抄文案）：显式声明「0 结果 ≠ 没记录」，并给出 ① 换更稀有的词（精确 ID / 路径 / 编号 优于描述性长句）② 放宽 `--since` / 去掉 `--kind` ③ 缓存可能滞后，先跑一次增量

## §4 明确不做（防膨胀，逐条给理由）

| 不做 | 理由 |
|---|---|
| **FTS5 / SQLite / 任何索引表** | rg 全扫 318 MB 只要 0.08~0.17 s、8~15 MB。索引的**唯一**收益是速度，而速度已经够了；代价是建表、迁移、损坏恢复、并发写。**净负收益。** |
| **向量 / embedding / 语义检索** | mimocode 零向量。语义检索解决的是"不知道用什么词"，而本需求的输入**恰恰是一条已知的记忆文本** → 关键词天然存在。 |
| **盖 sid 章（让归档条目自带会话 id）** | 有了全库文本缓存，条目→来源**不需要预存 sid**：直接拿条目里的字面量搜。盖章变成纯优化（缩窄搜索面），**可以永远不做**。 |
| **反向查漏报表**（`scanUndeposited` 的 raw 版） | 那是"分析报表"不是"检索"，且已有实测结论：编号类召回 **295/295 = 100%**。**本期不碰。** |
| **常驻 watcher / 后台服务** | 违反"常驻内存 0"；且日志是被 DSH 写的，watcher 要处理并发与生命周期。按需增量已足够。 |
| **脱敏** | 会破坏"逐字溯源"（用户要的就是原话）。改为**风险隔离**：不进 memory、不进同步目录、`README` 明确写出这是**明文副本**。 |
| **留存策略 / 自动清理** | 成本可接受（166 MB vs 713 MB 压缩日志），且删了就得重建。留 `--rebuild` / 手动删目录即可。 |
| **改 `memory_search` 的零结果引导文案** | 那需要改插件、重启。**列为后续可选**（见 §5）。 |

## §5 附带修复（**需插件改动 + 重启**，与主线解耦）

两条都是**实测发现的既有缺陷**，与"加功能"无关，可以单独取舍。

### §5.1 `decodeSessionLog` 改逐帧即弃

现行 `Buffer.concat` 路径在最大日志上 **932 MB / external 峰值 1541 MB / 11.7 s**；改逐帧即弃 → **187 MB / 4.7 s**。

- 批0 只修了它的 **O(n²) 拷贝**（性能），**没动峰值内存**
- 影响面：`decompressSessionLog` 的所有调用方（used 判定、子代理 token 统计）
- 风险：低（语义不变：返回全部帧的拼接文本；唯一变化是坏帧的处理顺序不变）

### §5.2 `resolveSessionLogPath` 单文件 → 多文件

对 §2.2 的 7 个劈开会话，现在的实现**只返回 v3**，早半段 **41.0 M 字符**对 漏网检测 / 帧数水位 / used 判定 / 归档提取 **永久不可见、零报错**。

- 改动：`resolveSessionLogPath` → `resolveSessionLogPaths`（返回数组），6 处调用点适配
- **有连带语义要拍**：`archiveWatermarks` 的帧数水位对这类会话要不要重算？`archivedSessions` 消号是否受影响？
- 风险：中（触及归档账本语义）→ **建议单独一期，不要和主线绑一起**

> §5 的两条**都不是本功能的必要条件**。若评审认为应拆开，主线可以**零插件改动**先交付。

## §6 验证门（含鉴别仪式）

**鉴别仪式铁律**：每条门必须先在"错误的/上一版的实现"上 **FAIL**，再在新实现上 PASS。否则门是假的。

| 编号 | 门 | 断言 |
|---|---|---|
| G1 | 幂等 | 连跑两次，第二次 **0 重写、0 变更**（mtime + 内容哈希均不变） |
| G2 | 增量等价 | 「增量构建结果」**逐行等于**「删掉缓存全量重建的结果」——最难也最容易错的一条 |
| G3 | 完整性守恒 | 每个样本：`保留行 + 显式丢弃行 == 原文非空行数`，且丢弃计数被打印（**不许静默丢**） |
| G4 | 逐字不改 | 抽 ≥50 条正文，与原文 `===` 全等（只允许换行转义差异） |
| G5 | 劈开会话 | 7 个已知案例：缓存必须**同时**含两个文件的正文；对 legacy 独有字面量必须命中 |
| G6 | 内存门 | 构建 27.3 MB 日志，OS 峰值工作集 **< 300 MB**（防有人改回 concat） |
| G7 | 检索门 | 已知字面量（中文 / Windows 路径 / 文号 / 函数名）命中，且 sid/行号/文件名全对 |
| G8 | 污染门 | `~/.dsh/session-text/` **不被**记忆库任何扫描读到（`scanUndeposited`、检索候选集、面板统计、预算告警） |
| G9 | 半截帧 | 人为截断日志尾部 → 不崩、不写坏缓存、**下次增量补回来**（且 `consumedFrames` 语义正确） |
| G10 | 口径版本 | 改 `KEEP` 集合 → **自动全量重建**，绝无新旧口径混合 |
| G11 | 原子性 | 构建中途 kill → 缓存要么是旧的完整版、要么是新的完整版，**永不半截** |

| R10 | §5 两条附带修复要不要本期做 | 倾向**拆开**，主线零插件改动先交付 |
