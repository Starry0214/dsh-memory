## 一、发现路径（不是搜出来的，是"不信上次结论"复查出来的）

§9.11.4-10 抢救 30 个之后，"仍无单元"从 103 降到 73。我对这 73 个做**逐会话复审**时发现：
`1c6f5d68` 有 4112 字真正文，却被首轮判成"无正文"。顺查其首轮 CSV 行 ⇒ `已落库=true` ⇒ 它**确实**已在
`sessions/2026-08-28.md` 里（判对了）。**但复审顺手抽查了另外几个"大帧却判无正文"的会话**，
发现真正的异常：日志里有大量 `text-chunks` / `reasoning-chunks` 事件，产品提取器却返回 `flow=0`。

## 二、机制（代码级，已定位到行）

`index.js` `extractMessageFlowAsync` 内的**事件类型白名单**（L4090–4095）只认六种：

```
user/message · assistant/message · system/message · tool/call · tool/result · compaction/summary
```

紧接着 L4096：

```js
if (!kd) continue;   // 非 KEEP 类（chunk 流等）体量最大，不逐个计数
```

**该注释自己点名了 "chunk 流"** ⇒ 是**已知且有意排除**，不是意外。全文件对 chunk 的唯一处理是
L10312：`assistant/chunk` **只用于读 `usage`**（计 token），**正文从不提取**。

⇒ **根因**：新式会话把助手输出写成**流式 chunk**（`text-chunks` / `reasoning-chunks` / `assistant/chunk`），
而提取器只认**已装配**的 `assistant/message`。于是这些会话：
- 提取器返回 `flow = 0`；
- 上层的 §9.11.4-3 落盘段据此写 `empty:true` 水位并**消号** ⇒ **永久不再进候选**。
