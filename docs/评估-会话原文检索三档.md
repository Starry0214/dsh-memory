## 1. 三档形态

### 档①「轻」：离线挖掘工具（批量、按需）
- **做法**：复用帧扫描解码器；输入关键词/日期/会话 id/cwd → 输出匹配行 + 出处（文件 + 帧号）。不做持久索引。
- **能力**：取证（找回摘要丢掉的字面量）、**漏查率度量**（回答"到底有没有人查过该查的东西"）、为档③准备解析逻辑。
- **不可用场景**：**会话中途"我想起某个词"**——全量 706.7 MB 逐帧解压是分钟级批处理，不是一次工具调用。
- **成本**：小（解码器现成）。新增一个脚本/工具 + 门。
- **风险**：**容易变成"写了一次从没人跑"的脚本**；且必须防"帧数=0 时静默返回空"（见 §0 解码陷阱）。

### 档②「中」：可回溯坐标（**我加的，可能是正解**）
- **做法**：**归档时给每条摘要条目记录源坐标**（`文件路径 + 帧号`，必要时加"该帧内首行 hash"做校验），而不是现在只有 `[ses YYYY-MM-DD]`。再配一个"按坐标取原文"的小工具：解压**单帧**（毫秒级）→ 返回原文。
- **能力**：**从任意记忆条目一跳回到原文** → **会话中途可用**（单帧解压 = ms 级）；不需要全文索引。
- **成本**：中——要改归档侧（`extractMessageFlowAsync` 的产物与摘要写入格式）+ 一个取原文工具 + 坐标校验。
- **要解决的真问题**：**坐标稳定性**。追加模式下帧号稳定；但文件被重写/轮转/改名（09-10 先例）后帧号会漂 ⇒ 必须有校验（帧头 + 内容 hash，不匹配则报"坐标失效"而不是返回错内容）。

### 档③「重」：持久增量索引（mimocode 路线）
- **做法**：扫原文 → 提取条目 → 建索引（SQLite FTS5，或 JS 侧倒排）→ `fingerprint` 增量 reconcile → 接入 `memory_search` 候选集。
- **能力**：**日常全文可搜**；"什么都不丢"成为事实 ⇒ **耐久层不再必要**。
- **成本**：**大**——2–3 GB 文本的索引体积、增量 reconcile、索引重建路径、并发（多 DSH 实例 last-write-wins 已知）、以及**分发约束**（单文件零依赖 → native sqlite 模块会破坏它；纯 JS 倒排要自建）。
- **新故障类**：索引陈旧/损坏 → **"记忆不可读"**。这恰是本插件一直刻意避免的（现设计"无索引 ⇒ 无陈旧故障类"）。mimocode 接受它，因为他们维护整层 DB。
- **必须先量**：706.7 MB 里**噪音占比**（工具输出/dump）——若过半是噪音，索引质量与体积都成问题（现有 `stripCompactionDumps` 与归档侧四类过滤可复用作门槛）。

## 2. 评审后结论（六席已回，**取代原"我的倾向"**）

> 原倾向里有两处被实测推翻，已在下面标注。

1. **档③（全文索引）——数据不支持做。** 全库召回实测（101 秒，见 §4）：**编号类召回 100%（295/295）**，即"最像不可再推导硬事实"的那一类**现有沉淀面已全中**，加索引**没有可回收的缺口**；总缺口 55.5% 经抽样以**噪声**为主（文档子页名/函数名/短语残片），**未经噪声过滤不得引用**。
   **若将来做，生死线不是体积而是"索引哪几类"**：只索引 `user/message` + `compaction/summary` ≈ **18 MB 文本 / 索引 4–9 MB**（可行）；含 `assistant/message` → 1.09 GB 文本 / 索引 220–550 MB（与单文件零依赖冲突，不可行）。
2. **档②（坐标回溯）——"技术成立，但不是答案"。** 原话"**档②可能是真正的解**"**撤回**：它确实**唯一**能补齐"记忆条目 → 原文"的断链（现有采样器把帧来源丢了），延迟 ~2 ms 也达标；但①**存量只有 11.3% 条目带溯源**（5,423 条目行 / 615 个 `[ses ]` 标记，其中 49 个还是日期区间形式）⇒ **只对未来条目生效**；②要改 **10 处**且含**两个 off-by-N 静默错位陷阱**（`L3134` splice 后需 `+skipFrames`、`L3321-3326` merge 时再 `+wm.frames`）；③坐标还得**进注入面**才兑现（每行 15–20 字符的 token 税）。
   **规格要点**：坐标**双写「帧起始字节偏移 + 帧号」**（偏移取原文 O(1)、帧号供人读）+ **帧内行号** + **解压后文本 hash**（唯一成功判据）；校验失败必须**显式报失效**，⛔ 不得 clamp 到邻帧、不得返回"最接近"的内容。
3. **档① 的形态定了**：做成**独立脚本是错的**（正合"写了一次没人跑"）——正确形态是**给已存在的 `scanUndeposited`（`index.js:1545`）加 `source:"raw"`**，复用 `L3129-3160` 帧扫描，挂现成的**非阻塞通道**（`danglingLegacyTxt`，`L9063-9109`），随 `/dream` 跑。**≤几十行**，且它的价值已被证明（**101 秒产出 §4 那组数**，可复跑）。
4. **与 fixed.md 的关系（红队框架，已采纳）**：三档**全是 pull，没有一档能替代 fixed 的"每会话在场"语义**。所以"先有检索再拆 fixed"的顺序要求**本身是错的**；拆 fixed 的独立代价不是"丢保护"，而是**正式接受遗忘风险**——这条须**单独向用户申报**，与做不做检索无关。
5. **两条硬纪律**：①任何新工具**必须复用**帧扫描解码器——整文件 `zstdDecompressSync` 会**静默返回首帧头（224–379 B）且不报错**（7/7 复现）；②**解码器的"空"必须可分辨**：今天 `no-frames` / `decode-error` / `no-content` / `ok` 四态**全都返回同一个 `null`**（`L3117`/`L3132`/`L3210`/`L3225`），调用方无法区分——档① 的度量若不分清，"空"会被读成"摘要没漏"，结论即污染。

## 4. 召回实测（决定档③ 的那个数）

命令：`node dsh-probe-recall.cjs <sessions> <memory>`（全 1065 文件，逐帧全解码，`wallSec 101`）

```
filesScanned 1065 | frames 1,445,856 | decMB 1974.7 | userMsgs 8,195 | userChars 11,889,166
全量      : literals 57,580 | hit 25,598 | recall 44.5% | gap 55.5%
非路径类  : literals 39,209 | miss 20,404 | recall 48.0% | gap 52.0%
编号类    : literals    295 | miss      0 | recall 100.0% | gap  0.0%
```

方法：逐帧全解码 → 取 `user/message` 的 text 块（同 `L3175` 过滤 `<system-reminder>`）→ 抽三类字面量（反引号 / 路径 / `(?:A)?20\d{8}`）→ 对沉淀面（knowledge + projects + tools + global + index + sessions + archive）做 `includes` 比对。

**结论（两条都要一起引，否则会被误用）**：
- **编号类（最像"不可再推导硬事实"的一类）召回 = 100%（295/295，miss 0）** ⇒ **现有沉淀面对这类已经全中**，加耐久层或全文索引**在这一类上没有可回收的缺口**。
- **55.5% / 52.0% 这两个缺口数不得直接引用**：抽样显示绝大部分是噪声（文档子页文件名 `cookies.md`/`tabs.md`、函数名 `list_cloud_profiles()`、变量 `BH_DOMAIN_SKILLS=1`、被分词切断的短语残片）。**真实事实缺口的具体百分比未证实**——需加"排除批量文件清单/碎片短语"的过滤后复测（这是档① 的下一件事）。

**未证实项**：① 真实事实缺口百分比；② 52% 缺口中噪声占比（仅抽样观察）；③ 全库行数 ≈2.49M（由 12 文件样本外推）。

## 5. ⚠ 阻断项：归档链上的四条**活缺陷**（与选哪一档无关，但污染档① 的全部度量）

来源：根因机制席第四轮；**主代理已逐行复核确认**（L5763/L5766/L5788-5794/L5800-5805/L5950-5951、L8429-8432、L3302/L5778-5780）。

| # | 缺陷 | 核实结果 | 后果 |
|---|---|---|---|
| **1** | **提取失败 = 永久跳过** | `L5763` 取帧数 → **`L5766` 先记 `batchFrames`** → 再提取；失败走 `L5793 skippedNoFlow` → **`L5800-5803` 把 skipped 加进 `handledIds`（当成功处置）** → `L5950-5951` `ARCHIVED_SESSIONS.add` + **水位写成当前帧数** | 该会话的帧**永远不会再被提取**，且**不可观测**（只有全批无流才单列 `L5808`） |
| **2** | **`slice(-300)` 上限** | `L8429-8432`：`staleNotified`/`archivedSessions`/`archiveWatermarks` **只存最后 300 个 id** | 超限后最旧 id 丢失 → 重启后不在 `ARCHIVED_SESSIONS` → 重复归档，或走懒置基线**把期间尾帧静默吞掉**。**盘上实测：280/300，只剩 20 个位** |
| **3** | **缓存无身份校验 + 失败时当成功** | `L3302` `readUnitCache` **只校验 `typeof d.text === "string"`**（不校验 sid/frames/round/源文件）；`L5778-5780` 在新增帧提取失败时**回退旧缓存并标为本轮成功单元** | 归档子代理拿到旧内容、报成功、新帧从此不见 |
| **4** | 双解码器容错方向相反 | ⚠ **未核实**（采信）：`decompressSessionLog`（`L3101-3118`）catch 在 while **外** → 单帧坏 = 整文件 `null`（`L3491` 当"已用"、`L8380` token 统计静默缺失）；`L8378` 注释"已消除两套循环"与事实不符；`Buffer.concat` 在循环内 = O(n²) | 见左 |

**盘上旁证**：`archivedSessions` **280**（上限 300）、水位时间戳跨度 **08-30 → 09-17**、原文日志 **1065 个**。⚠ 差额 785 **未分解**（顶层会话 vs 子代理会话；归档流程只覆盖顶层）⇒ **不得据此断言"785 个丢了"**。

**对档① 的影响（关键）**：档① 测的是"摘要层漏掉了什么"，而缺陷 1/3 会让部分会话**根本没被提取** → 测出的"缺口"里混着"归档失败"。**⇒ 必须先修 §5，档① 的度量才可用。**
